# DramaX 钱包连接 DApp 支付整改方案 V1.0

> 目标：取消「手动转账 + 手动提交 txid + 异步核验/申诉仲裁」模式，改为用户连接 Web3 钱包、在 DApp 内直接完成链上支付，平台通过链上事件监听自动入账与核验。
> 依据：《DramaX_技术架构设计_V1.0》《链路线与USDT入金》《商业逻辑总结 V2.1》
> 日期：2026-08-29

---

## 1. 整改背景与目标

### 1.1 现状痛点

| 环节 | 现状 | 痛点 |
|---|---|---|
| 入金 | 专属充值地址 + 用户手动转账 + 提交 txid + 链上核验 Job | 用户操作步骤多；txid 漏填/错填/延迟；假币需白名单校验兜底 |
| P2P 付款 | 买家线下转账给卖家 + 60 分钟 txid 核验窗口 | 金额匹配歧义（同地址多笔同额）；超时申诉仲裁人工成本高；欺诈窗口期 |
| 对账 | 双向核对 txid | 账实核对链路长，出错恢复难 |

### 1.2 整改目标

1. **入金**：钱包连接 → DApp 内发起 USDT 转账 → 平台监听链上事件 → 确认数达标自动入账。用户全程不离开页面，不接触 txid 概念。
2. **P2P 付款**：买家在 DApp 内向卖家收款地址直接发起转账（带订单绑定），Indexer 监听到账自动核验，消灭申诉主路径。
3. **非托管原则**：平台不碰用户私钥、不托管用户钱包资产；支付动作完全由用户钱包签名发起。

## 2. 链与钱包选型（定调）

| 项 | 决策 | 理由 |
|---|---|---|
| 支付链 | **BSC（BEP-20 USDT）为唯一 DApp 支付链** | 钱包普及率高（MetaMask/OKX/TokenPocket 全支持）；gas 低；合约生态成熟 |
| TRC-20 通道 | **降级为过渡兼容通道（保留 4–8 周），随后下线** | Tron 生态无法做标准 DApp 签名交互（无 injected provider 事实标准），手工 txid 模式不再投入开发 |
| 钱包接入 | EIP-1193 injected provider（MetaMask/OKX/TokenPocket 内置浏览器）+ **WalletConnect v2**（扫码/移动端） | 双通道覆盖桌面 + 移动 |
| 支付代币 | 仅 USDT（合约 `0x55d398...7955`），白名单硬编码 | 单一代币，杜绝假币问题（直接监听官方合约 Transfer 事件，假币在协议层不存在） |

> 注意：DApp 模式下「假币校验」从业务层校验降级为「只监听官方 USDT 合约地址」，天然免疫假币。

## 3. 总体支付链路（目标态）

```
┌──────────┐   ①connect    ┌──────────┐  ②创建支付意图   ┌──────────┐
│ 用户钱包   │ ←──────────→ │ DApp 前端 │ ──────────────→ │ 平台后端   │
│(MetaMask/ │               │          │   (orderId+金额盐)│(Payment   │
│ OKX/WC2) │               │          │ ←────────────── │ Intent)   │
└────┬─────┘               └────┬─────┘    返回支付参数    └────┬─────┘
     │  ③用户签名 USDT.transfer(收款地址, 盐值金额)              │
     ▼                        ▼                              ▼
┌─────────────────────────────────┐              ┌──────────────────┐
│ BSC 链上（USDT 合约 Transfer 事件）│ ──④监听──→ │ Indexer 集群       │
└─────────────────────────────────┘              │ ·解析 Transfer     │
                                                  │ ·金额盐反查订单    │
                                                  │ ·≥15 确认 → 入账  │
                                                  │ ·幂等（tx_hash 唯一）│
                                                  └────────┬─────────┘
                                    ⑤入账/核验通过            ▼
                                       ┌────────────────────────────┐
                                       │ 双账本（Drama/积分）+ 状态机推进 │
                                       └────────────────────────────┘
```

### 3.1 订单绑定方案（关键设计决策）

普通 ERC-20 `transfer` 不带 memo，订单绑定三选一：

| 方案 | 原理 | 优点 | 缺点 | 采用 |
|---|---|---|---|---|
| A. 金额盐值 | 支付金额 = 订单金额 + 唯一分位盐（如 100.00 + 0.37 USDT），Indexer 按金额反查 | 无需合约，1 天上线 | 盐值泄露可被撞库；用户看到非整数金额 | **P0 过渡采用** |
| B. 专属归集地址 | 每用户/每订单派生独立收款地址（HD 派生） | 无合约、隐私好 | 地址管理复杂，归集 gas 成本 | 备选 |
| C. Deposit Registry 合约 | 用户调合约 `deposit(orderId)`，合约代转 USDT 并发事件（含 orderId） | 绑定最干净、可扩展 Escrow | 需合约开发 + 审计（2–4 周） | **P1 落地，替换 A** |

**结论**：P0 用方案 A 快速上线；P1 部署 Deposit Registry 合约后切换方案 C；方案 A 下线。

## 4. 分模块整改清单

### 4.1 前端（DApp 化）

| # | 整改项 | 说明 |
|---|---|---|
| F1 | 钱包连接模块 | EIP-1193 + WalletConnect v2 双通道；连接状态全局管理（地址/链 ID/余额）；chainId ≠ 56（BSC 主网）时引导一键切链（`wallet_switchEthereumChain`） |
| F2 | 支付确认弹层 | 展示：收款地址（可复制校验）、金额（含盐值说明「含 0.37 系统识别码」）、预估 gas；明确「支付由您的钱包签名，平台不接触私钥」 |
| F3 | 支付状态页 | 广播中 → 已上链（等待确认 x/15）→ 已入账；轮询后端支付意图状态，禁止依赖前端读链 |
| F4 | 入金页改造 | 原「复制充值地址 + 提交 txid」表单下线 → 「连接钱包支付」单按钮 |
| F5 | P2P 付款改造 | MATCHED 态「提交付款凭证」→「钱包支付」按钮；卖家收款地址由后端下发并展示 |
| F6 | 钱包未安装降级 | 展示收款地址 + 金额盐（仍走方案 A 人工路径，Indexer 兜底监听），提示建议安装钱包 |

### 4.2 后端 / Indexer

| # | 整改项 | 说明 |
|---|---|---|
| B1 | Payment Intent API | `POST /payments/intent`：生成 orderId + 金额盐（盐空间预留防撞：金额分位 2 位，同订单 5 分钟失效重生成）；Redis 存 intent→订单映射，TTL 30 分钟 |
| B2 | **Indexer 集群（新增核心组件）** | 订阅 BSC 节点（自建全节点或 QuickNode/Ankr），解析 USDT 合约 Transfer 事件；关注两类地址：平台归集地址池、卖家收款地址池；写 `chain_events` 原始事件表（tx_hash 唯一索引，天然幂等） |
| B3 | 确认策略 | BSC 3s/块，**15 确认 ≈ 45 秒**（沿用现有确认口径）；处理 reorg：`chain_events` 记录 block_hash，检测到重组回滚则撤销未入账事件并告警 |
| B4 | 入账引擎 | 事件确认达标 → 盐值/合约事件反查订单 → 校验金额（≥ 应付，多余部分退回或转余额，拍板项）→ 双账本幂等入账 |
| B5 | 核验引擎（P2P） | 监听卖家地址入账 → 金额匹配盐值 → 自动置 MATCHED→SOLD；**60 分钟窗口改为「支付广播监听窗口」：买家点击支付后 15 分钟内未检测到上链 → 订单回滚**（链上支付不再需要 60 分钟） |
| B6 | 资金归集 Job | 平台归集地址余额 > 阈值 → 归集至冷钱包（多签），归集 tx 记录台账 |
| B7 | 对账 Job | 每日：`Σ(chain_events 确认入账)` vs `Σ(双账本入金)` vs `Σ(归集流水)` 三方核对 |

### 4.3 合约层（P1）

| 合约 | 功能 | 安全 |
|---|---|---|
| DepositRegistry | `deposit(orderId)` → 转 USDT → 事件 `Deposited(orderId, from, amount)`；仅接受白名单 USDT | 可升级代理（Transparent Proxy）+ 多签管理员 |
| EscrowP2P（P2 远期） | 买家锁仓 → 卖家确认释放 / 超时仲裁回滚 | 沿用 KolMarket multisig 治理经验（2/3 阈值） |

### 4.4 数据模型变更（对 V1.0 ER 的增量）

```sql
-- 新增
chain_events(tx_hash PK, block_no, block_hash, log_index, contract_addr,
             from_addr, to_addr, amount, status(0待确认/1确认/2回滚), intent_id)
payment_intents(id, order_type(DEPOSIT/P2P), order_id, payee_addr,
             salt_amount, expires_at, status)

-- 修改
deposits:   新增 tx_hash/payment_intent_id 由 Indexer 回写；status 流转改为
            PENDING→BROADCAST→CONFIRMED(15)→CREDITED；用户提交 txid 字段废弃保留兼容
matches:    buyer_txid 废弃 → payment_intent_id；verify_deadline 60min → 15min 广播窗口
```

### 4.5 状态机变更

```
入金：  创建意图 → BROADCAST(检测到上链) → CONFIRMED(15确认) → CREDITED(入账)
P2P：   MATCHED → PAYING(买家点支付, 15min 广播窗口) → 链上到账自动核验 → SOLD
        （原「提交 txid → 60min 人工核验窗口 → 申诉仲裁」主路径废除，
          申诉仅保留为 Indexer 异常兜底）
```

## 5. 合规影响评估

| 项 | 整改前（托管入金） | 整改后（DApp 非托管） | 评估 |
|---|---|---|---|
| 资金托管 | 平台地址收款 = 事实托管 | 用户钱包直付，平台仅做账务记录 | **风险下降**（非托管定性更清晰） |
| 9.24 红线 | 涉虚拟货币业务 | 不变，仍需**海外主体 + 中国大陆 IP/身份区域屏蔽** | 不变，硬约束 |
| 反洗钱 | txid 人工审查 | 链上全量可溯（from/to 天然记录） | 可加地址风控黑名单（Tornado 等混币源标记） |
| VASP/MSB | 需评估 | 若引入 Escrow 托管合约，托管属性需重新评估 | P2 阶段法务复核 |

## 6. 排期与工作量

| 阶段 | 内容 | 工期 | 依赖 |
|---|---|---|---|
| **P0（快速上线）** | F1–F5 前端钱包接入、B1 意图 API、B2/B3 Indexer + 确认策略、方案 A 金额盐绑定、B4/B5 入账与核验引擎 | 2–3 周 | BSC 节点/第三方 RPC 选型 |
| **P1（合约化）** | DepositRegistry 合约 + 审计、方案 C 切换、方案 A 下线、B6/B7 归集与对账 Job、TRC-20 手工通道下线 | 3–4 周（含审计） | P0 稳定运行 |
| **P2（托管升级）** | EscrowP2P 合约 + 多签仲裁、P2P 全自动交割、地址风控黑名单 | 4–6 周 | 法务复核托管定性 |

## 7. 需要拍板的事项

1. ⛔ **超额支付处理**：盐值方案下用户多付（余额盐生效期内重复支付），差额退回链上还是转平台余额？
2. ⛔ **BSC 节点方案**：自建全节点（成本高、可控）vs QuickNode/Ankr 付费 RPC（快速、月费）？
3. ⛔ **15 确认口径**：BSC 出块 3s，15 确认仅 45 秒，是否沿用原口径（建议沿用，安全边际足够）？
4. TRC-20 过渡通道保留时长（建议 4–8 周后下线）。

## 8. 整改对照总表（Before → After）

| 场景 | Before | After |
|---|---|---|
| 入金 | 复制地址 → 外部转账 → 手动填 txid → 等待核验 | 连接钱包 → 点支付 → 45 秒自动入账 |
| P2P 付款 | 线下转账 → 手动提交凭证 → 60min 核验 → 争议仲裁 | DApp 内直付卖家 → 链上到账自动核验 → SOLD |
| 假币风险 | 白名单合约校验兜底 | 协议层免疫（只监听官方 USDT 合约） |
| 申诉仲裁 | 主路径 | 兜底（Indexer 异常时启用） |
| 用户教学成本 | 高（需懂转账/txid/确认数） | 低（一次钱包授权，后续一键支付） |
